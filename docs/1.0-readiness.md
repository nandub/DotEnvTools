# 1.0 Readiness Checklist

Use this checklist before cutting the first stable `1.0.0` release.

## Public API

- Confirm exported command names in `Source\DotEnvTools.psd1`.
- Confirm parameter names, defaults, and aliases.
- Avoid breaking renames after `1.0.0` unless a major version bump is planned.
- Keep the module `GUID` unchanged.

## Compatibility

- Run CI on Ubuntu, Windows, and macOS.
- Run local quality checks on Windows PowerShell 5.1 when practical.
- Confirm packaged `Get-Help` works from `Source\en-US\DotEnvTools-help.xml`.
- Confirm generated files work on case-sensitive filesystems.

## Documentation

- Verify README quick start from a clean clone.
- Verify examples use only exported public commands.
- Regenerate Markdown and external help after command help changes:

```powershell
.\scripts\Update-DotEnvToolsHelp.ps1 -ModuleRoot . -Force
```

- Confirm `CHANGELOG.md` has a `1.0.0` entry with user-facing release notes.
- Confirm `docs\release-process.md` matches the actual release flow.

## Packaging

- Run quality checks:

```powershell
.\scripts\Test-DotEnvToolsQuality.ps1 -ModuleRoot . -RunAnalyzer -RunTests
```

- Build the release package:

```powershell
.\scripts\Build-DotEnvTools.ps1 -NewVersion 1.0.0 -Verbose
```

- Validate the module manifest:

```powershell
Test-ModuleManifest -Path .\dist\DotEnvTools\1.0.0\DotEnvTools.psd1
```

- Smoke import the built module and run a basic workflow.

## Publishing

- Create a GitHub Release with `dist\DotEnvTools-1.0.0.zip` attached.
- Publish to PowerShell Gallery only after the release candidate has passed CI and manual smoke testing.
- Keep GitHub Packages optional unless repository-scoped package feeds become useful.
